# Images and instances

Both live in the namespace `t-<tenant>` of the `phorge.fr` group.

- **An instance starts from an image of its tenant**, never from a bare image name: the API refuses an image that does not exist in the tenant (`422`) and one that is not `Ready` yet (`409`, `image_not_ready`). While it is pulled (a few minutes) an instance would report problems that are not one and be called `Failed` after three minutes.
- **Images** are pulled from the `images` server (linuxcontainers.org) only, as virtual machines for the architecture of the compute nodes. The Image kind is the only gate to the image servers, so the API restricts the remote. An image cannot be changed, only deleted, and pulled again.
- **Deleting an image** that instances start from is a `409` that names them. Delete them first.
- **Instances**: `cpu` 1 to 16, `memoryMiB` 256 to 65536, `diskGiB` 1 to 500, the rest is what the platform decides (what is not given is not sent). `PATCH` changes `running` (start and stop keep the same VM), `networks`, `cpu`, `memoryMiB`, `diskGiB` and `sshPublicKeys`, applied live. The memory of a **running** instance can only be raised: Incus refuses a lower one (`failed to resize memfd`), so the API answers `409` with the code `running` and the request is not sent, whether it comes by `memoryMiB` or by a profile that comes to less. To lower it, stop the instance, change the memory, then start it again: a change of size never starts or stops an instance by itself, the power state changes only when the request asks for it with `running`. The image, `nesting` and `secureBoot` cannot change: delete and create.
- **The settings of an instance are read as they are in force.** `nesting`, `secureBoot` and `sshPublicKeys` of an instance read through the API are what the VM has, not only what the object says. The `Instance` kind has no default for them: an absent field means the instance did not say, and its profile, or else the default (nesting off, secure boot on, no key), applies. The platform writes the value in force in `status.nesting`, `status.secureBoot` and `status.sshPublicKeys`. The API reads each one from `spec` when the object says it (an instance created before the change has the three stored, written by the old defaults), else from `status`, else from the default, so an instance created without `secureBoot` is shown with `secureBoot: true` before and after the platform stops defaulting it. The field being absent is what counts, never its value: an absent `secureBoot` is not `false`. `spec` comes first because the API writes it (`PATCH` of `sshPublicKeys`) and the status follows a moment later, so the reply to a change shows the new keys; once the status has caught up both are the same, because what the instance says wins over its profile. A request that does not give these fields sends none of them.
- **The quota of the plan is checked by the API first**: a request that would pass it is refused with `409` and the code `quota_exceeded`, before Incus is asked (see [Limits and quotas](limits-and-quotas.md)). Incus stays the authority, and a refusal of its own, such as `Reached maximum number of instances`, comes back as the `problems` of the instance, in words (`This tenant has reached the maximum number of instances of its plan.`), and the instance becomes `Failed` after three minutes. Stopped VMs count. An instance whose first start failed is stuck: delete it and create it again.
- **SSH keys are checked strictly.** The composition writes them into the cloud-init of the VM with a plain `printf`, one `- <key>` line per key, indented by two spaces, and nothing else protects it: a line break in a key would add a line of cloud-init, a command run as root in the VM. A key is accepted only as `<type> <base64>` and at most a one word comment of letters, digits and `@._+=/-`.
- **An instance is on one or several networks of its tenant** (`networks`, a list of 1 to 8, see [Networks](networks.md)): named in the request, or the only one of the tenant. `PATCH` replaces the list, live, without a restart. `network` is the deprecated way to give one.
- **The size of an instance is a profile or its own values, never both.** `profile` is one of `GET /v1/tenants/{t}/profiles` (`s` 1 vCPU, 2 GiB, 64 GiB; `m` 2, 4, 128; `l` 4, 8, 256); the other way is `cpu`, `memoryMiB` and `diskGiB`, and what a request leaves out takes 1, 1024 and 10 (the Crossplane kind has no defaults, the API completes the size). A profile with a value is `422`, so is a profile that does not exist, and the answer lists the profiles. The body of an instance carries its `profile` and, in every case, the `cpu`, `memoryMiB` and `diskGiB` it comes to. `GET /v1/limits` has the bounds.
- **A size changes in place**: `PATCH` with a `profile` moves the instance to it and removes its own values; an instance that has a profile leaves it by being given the three values together (a value alone is `422`, it would sit next to the profile). Incus applies it live on a stopped instance.
- **The resources of a plan hold two instances of its own profile size** (`small` two `s`, `medium` two `m`, `large` two `l`), and the count of instances is 2, 4 and 6: an instance that asks for more than what is left is refused with the limit it passes, before Incus is asked (see [Limits and quotas](limits-and-quotas.md)).
- **A user makes their own profiles** (`POST /v1/tenants/{t}/profiles`): CPU, memory and disk, all three given, under a name of 1 to 32 characters (`s`, `m`, `l` and `default` are taken, `422`). They are listed after the three every tenant has, with a phase and what is wrong in words. An instance takes one as it takes `s`, `m` or `l`, and counts in the quota what it comes to. Deleting one is refused (`409`, `in_use`) while an instance has it, and names the instances; `s`, `m` and `l` are not changed nor deleted (`403`). A tenant holds at most `MAX_PROFILES_PER_TENANT` of them. A profile may also say two settings of an instance, `secureBoot` and `sshPublicKeys` (up to 20, checked as the keys of an instance, see the item on SSH keys). They are written on the object only when the request gives them: a profile that does not say one has none, and the body shows none, so an absent `secureBoot` is not `false`. An empty list is the same as none. An instance takes the settings of its profile unless it says its own: keys given by the instance replace the profile's, they do not add to them. A profile never has a network nor `nesting` (Incus refuses nesting on a profile of a tenant project, so nesting stays a setting of the instance): a request with either is `400`, an unknown field. Changing a profile in place is not in the API: make another one and move the instances to it.
